Сделай релиз приложения. Работай в `/Users/stanislav/Documents/it/cash/my-app`. Не задавай лишних вопросов и не запускай проверки (typecheck, lint, тесты): пользователь их не хочет, TypeScript и так проверяется при сборке в Docker.

Если пользователь передал аргумент (`major`, `minor` или `patch`), используй именно этот тип повышения версии. Иначе выбери его сам по правилам ниже.

## 1. Что изменилось с прошлого релиза

- Текущая версия: поле `version` в `package.json`.
- Найди прошлый релиз: последний коммит `release vX.Y.Z` (`git log --grep '^release v' -1 --format=%H`). Если такого коммита нет (так вышла версия 1.1.0), возьми коммиты, сделанные после даты последней записи `app_changelog` (`git log --since=<released_on>`), и не включай то, что уже описано в её пунктах.
- Собери изменения: `git log <прошлый релиз>..HEAD`, `git diff <прошлый релиз>` и незакоммиченные правки (`git status`, `git diff`). Учти также текущую беседу.
- Если изменений нет, скажи об этом и остановись.

## 2. Номер версии (semver)

Формат `MAJOR.MINOR.PATCH`:

- **patch**: только исправления ошибок и мелкие правки внешнего вида, новых возможностей нет;
- **minor**: есть хотя бы одна новая видимая пользователю возможность или заметное изменение поведения;
- **major**: несовместимые изменения (меняется смысл данных или привычная работа, нужна ручная миграция пользователям) либо полный редизайн. Применяй редко.

Берётся самый высокий уровень из всех изменений. Новую версию запиши в `package.json` (поле `version`), остальное в файле не трогай.

## 3. Пункты списка изменений

- Язык русский, пишет для пользователя приложения, а не для разработчика.
- Один пункт одно изменение, коротко: одна строка, до 80 символов, без точки в конце.
- Описывай, что стало для пользователя («Вкладка «Итог» в разовом бюджете»), а не как это сделано в коде.
- Не включай внутреннее: рефакторинг, деплой, инфраструктуру, правки конфигов, сам механизм версий и списка изменений.
- Объединяй похожие правки в один пункт. Обычно 3-10 пунктов.
- Исправления ошибок начинай со слова «Исправлено:».

## 4. Порядок действий

1. Обнови `version` в `package.json`.
2. Закоммить всё накопленное одним коммитом с сообщением `release vX.Y.Z` (с подписью Devin по общим правилам git). Только коммит: без тега и без push.
3. Задеплой: `./deploy.sh` (вывод можно отфильтровать по строкам `==>`, `rror`, `Compiled`, `Recreate`, `Started`). Если сборка упала по сети (например, `EAI_AGAIN` при загрузке yarn), повтори один раз. При другой ошибке остановись и сообщи; запись в БД не делай.
4. После успешного деплоя запиши список изменений в таблицу `app_changelog` прод-базы (см. ниже).
5. Проверь, что `https://hiveapp.online/budgets` отвечает (ожидаемо 307).

## 5. Запись в БД

Локальная разработка и этот скрипт ходят в прод-базу через SSH-туннель на `127.0.0.1:5432` (`yarn dev` его поднимает). Перед записью проверь, что порт слушается (`lsof -nP -iTCP:5432 -sTCP:LISTEN`); если нет, запусти `bash scripts/db-tunnel.sh` в фоне. Никогда не выводи `DATABASE_URL` и пароли.

Дата релиза сегодняшняя (`date +%F`). Выполни, подставив версию, дату и пункты:

```bash
node - <<'EOF'
const postgres = require('postgres');
const url = require('fs').readFileSync('.env.local', 'utf8').match(/^DATABASE_URL=(.*)$/m)[1];
const sql = postgres(url);
(async () => {
  const items = [/* пункты строками */];
  await sql`insert into app_changelog (version, released_on, items) values (${'X.Y.Z'}, ${'YYYY-MM-DD'}, ${items}) on conflict (version) do nothing`;
  console.log(await sql`select version, released_on, array_length(items,1) as n from app_changelog order by released_on desc, created_at desc limit 3`);
  await sql.end();
})().catch((e) => { console.error(e.message); process.exit(1); });
EOF
```

Схема таблицы: `server/db/schema/changelog.ts` (`version` уникальная, `released_on` дата, `items` массив текста). Не меняй схему и не запускай миграции в этом skill.
